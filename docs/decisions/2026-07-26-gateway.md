# Decision: the gateway is opt-in, never the default path

**Date:** 2026-07-26
**Status:** Accepted
**Affects:** PR #5 (`feat/gateway`)

## Context

PR #5 adds a full local gateway service under `packages/gateway/`: an Express
server, SQLite usage logging, an org policy engine, admin routes, an admin-key
mechanism, BYOK support, and tests. It is substantial, well-structured work.

The extension side of the same PR wires it in like this:

```ts
// packages/pixa-agent/src/config.ts
export const DEFAULT_GATEWAY_URL = "http://localhost:8080/v1/chat";
```

and `extension.ts` calls `ensureGatewayRunning(...)` during activation, which
spawns the gateway as a child process. `OpenRouterProvider` then routes through
`this.gatewayUrl || (this.id === "openrouter" ? DEFAULT_GATEWAY_URL : ...)`.

The practical effect: **every OpenRouter user gets a locally spawned server
process by default**, whether they wanted one or not.

## The conflict

This contradicts the product positioning we shipped and published:

- `README.md` states, verbatim: "No vendor lock-in. No telemetry. **No required
  server.**"
- The open-source pitch is "clone and it just works" — a solo developer
  installing from the Marketplace should need an API key and nothing else.
- We already rejected a required-server architecture once, when we chose
  config-file provider setup (`pixa.providers`) over a gateway for custom
  providers.

A background process the user did not ask for is also a support burden (port
conflicts on 8080, orphaned processes, firewall prompts) and an unexpected
attack surface for a tool whose main selling point is that your code stays on
your machine.

## Decision

**Adopt the gateway as an opt-in feature. Do not make it the default.**

Concretely, before `feat/gateway` can merge:

1. **No implicit default.** Remove `DEFAULT_GATEWAY_URL` as a fallback. If
   `pixa.gatewayUrl` is unset, the extension talks to the provider directly,
   exactly as it does today.
2. **No auto-spawn.** `ensureGatewayRunning` must not run on activation. Starting
   the gateway is an explicit user action (a command, or a documented
   `npm start -w pixa-gateway`).
3. **Direct provider mode stays the tested default.** The existing
   `localProvider.test.ts` behaviour — no gateway, no server — must remain
   green and remain the documented path in the README.

Under those conditions the gateway is genuinely valuable, and we want it: shared
keys, per-org spend policy, usage audit, and BYOK are real needs for the team and
enterprise use case that the extension alone cannot serve.

## Why not just merge it as-is

Because the default path is a product decision, not an implementation detail.
Shipping it as the default would make our own README untrue on the day we
launched it publicly.

## Why not reject it outright

The gateway code is sound and the enterprise need is real. Rejecting the work
would discard ~1,100 lines of functioning server code plus tests over a wiring
decision that is a few lines to change.

## Immediate consequence: unbundle the reasoning-effort work

`feat/gateway` also contains an unrelated, wanted feature: reasoning-effort
support (`ReasoningEffort` type, `supportsReasoningEffort` capability flag on
`ModelEntry`, OpenRouter's `reasoning: { effort }` body field, a UI selector, and
`test/reasoningEffort.test.ts` — 351 lines of tests).

That work is architecturally independent of the gateway and follows the existing
capability-flag pattern (`supportsTools`). It should be **extracted into its own
PR and merged on its own merits**, so it is not held hostage to the gateway
decision.
